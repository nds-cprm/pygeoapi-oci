# CLAUDE.md

Este arquivo orienta o Claude Code (claude.ai/code) no trabalho com este repositório.

## O que é

Um repositório para gerar uma imagem de contêiner OCI do [pygeoapi](https://pygeoapi.io) (servidor Python para os padrões OGC API), servido pelo uWSGI com o **protocolo uwsgi** (não HTTP) na porta 8000, atrás do nginx como proxy reverso (exemplo com Compose em [examples/](examples/README.md)), como no mapproxy-oci. Há dois workflows: o de build (`.github/workflows/docker-image.yml`) e o que mantém os locks (`.github/workflows/update-locks.yml`). Não há testes unitários; o teste é o de fumaça da imagem (`.github/scripts/smoke-test.sh`), rodado pelo CI. Licença Apache-2.0.

## Arquivos

- `Dockerfile`: build em três estágios sobre `docker.io/ndscprm/gdal:${GDAL_VERSION}-py${PYTHON_VERSION}-${BASE_DATE}` (Debian trixie, Python oficial e GDAL instalado em `/opt/geosgb`, com o venv em `/opt/geosgb/venv` no `PATH`). Os estágios `schemas` e `wheels` usam a variante `-devel` da mesma data (`${GDAL_VERSION}-py${PYTHON_VERSION}-devel-${BASE_DATE}`), que traz `gcc`, `make`, os headers do Python e do GDAL, as bibliotecas `-dev`, além de `wget`, `curl` e `unzip`. A base é fixada pela tag datada, e não pelas tags sem data (`3.12.4-py3.12` e `3.12.4-py3.12-devel`), que o gdal-oci reconstrói no lugar toda semana. As datadas nunca são sobrescritas. Um segundo build no mesmo dia ganha `.2`, `.3`..., e a `-devel` e a de runtime de um mesmo build têm a mesma data. As tags disponíveis estão em `https://hub.docker.com/v2/repositories/ndscprm/gdal/tags?name=<gdal>-py<python>`.
  - Estágio `schemas`: baixa o `SCHEMAS_OPENGIS_NET.zip` via HTTPS, confere o SHA-256 dele com o `ARG OGC_SCHEMAS_SHA256` e extrai apenas `ogcapi/*` em `/schemas.opengis.net`, para que os schemas OGC sejam servidos localmente em vez de baixados em tempo de execução. A `-devel` já tem `wget` e `unzip`, que a imagem de runtime não tem, então não é preciso `apt-get`. O estágio fica separado do `wheels` para ter cache independente (mudar dependências não baixa o zip de novo) e para os dois serem construídos em paralelo. Pode ser gerado sozinho com `--target schemas`.
  - Estágio `wheels` (`-devel`): grava em `/wheels`, em duas camadas. Primeiro escolhe o lock `requirements/pygeoapi/${PYGEOAPI_VERSION}.txt` e, se ele não existir, para com uma mensagem mandando rodar o script para aquela versão. Depois roda `pip wheel --require-hashes --no-deps` para o lock, com as versões dos pacotes que a própria imagem já traz como restrições (`-c`, geradas no build com `pip freeze --all`). O `--no-deps` faz o pip baixar só o que está no lock, sem buscar de novo o numpy e os outros pacotes da base. Por último roda `pip wheel --require-hashes --no-deps` para o lock dos extras da mesma versão, `requirements/extra/${PYGEOAPI_VERSION}.txt`, com o lock do pygeoapi como restrição. Se esse arquivo não existir, para com `no extras lock for pygeoapi X`. Nessa restrição, os hashes são removidos com `sed`: se ficassem, o pip exigiria hashes também para os pacotes do lock do pygeoapi, que esse passo não baixa. O lock dos extras deixa de fora o que o do pygeoapi já tem (hoje `requests`, `urllib3`, `certifi`, `python-dateutil` e `six`, puxados pelo `opensearch-py`). Com o `--no-deps`, esses pacotes não são baixados de novo, e nenhuma wheel binária de um pacote do `NO_BINARY` entra em `/wheels` por um extra. Como cada um tem sua camada, mudar só os extras não refaz as wheels do pygeoapi. Pacotes sem wheel binária, como o uWSGI, são compilados ali, contra o mesmo Python e GDAL do estágio final. Os do `ARG NO_BINARY` (`rasterio,pyproj,shapely`, só nomes, separados por vírgula) também são compilados a partir do sdist, cujo hash está no lock, contra o GDAL, o PROJ e o GEOS da base. Os demais são só baixados. A versão de cada um vem do lock, e o build mostra no log o que vai compilar (`building rasterio==1.5.2 from its sdist`). Se um nome do `NO_BINARY` não estiver no lock, o build falha antes de compilar, com `<nome> (NO_BINARY) is not in the lock of pygeoapi X`. Isso pega erros de digitação e pacotes que a versão do pygeoapi deixou de usar. Para compilar outro módulo do lock, acrescente o nome ao `NO_BINARY`. Ele também pode ser trocado com `--build-arg NO_BINARY=...`. A `-devel` tem os headers do PROJ (`libproj-dev`), mas não o executável `proj`, que o setup do `pyproj` procura. Por isso, o `pip wheel` recebe `PROJ_DIR=/usr` e `PROJ_VERSION=$(pkg-config --modversion proj)`. As dependências de build dos sdists rodam num ambiente isolado, que o `-c` não alcança: um teste com `numpy==2.3.0` mostrou que o `-c` e o `PIP_CONSTRAINT` são ignorados ali e só o `--build-constraint` é respeitado. Por isso, os dois `pip wheel` recebem `--build-constraint` com o freeze da base, que fixa o numpy (2.5.4), o setuptools e os demais pacotes da base também no build. Cython, meson e meson-python não estão na base e continuam sem versão fixa e sem hash. Nenhuma dependência de build vai para a imagem final. O `pip wheel` roda com `LDFLAGS=-s`, então tudo o que é compilado ali sai sem símbolos de depuração, como faz a imagem base. Isso precisa ser feito nesse estágio, porque a imagem de runtime não tem `strip`.
  - Estágio final:
    1. Instala as dependências com `pip install --no-index --find-links /wheels`, a partir das wheels montadas do estágio `wheels`, em dois `RUN`. O primeiro instala o lock do `PYGEOAPI_VERSION`, sem os hashes (removidos com `sed`) e com o `pip freeze --all` da imagem de runtime como restrições, para que nenhuma dependência troque o GDAL, o numpy ou outro pacote da base. Esse passo resolve as dependências, então falha se o lock estiver incompleto. Os hashes não são verificados de novo aqui. Eles já foram conferidos quando o estágio `wheels` baixou cada arquivo, e as wheels compiladas ali (`NO_BINARY`) não teriam hash do PyPI para bater. O segundo instala o lock dos extras, também sem os hashes (o uWSGI é compilado no estágio `wheels`), com o `pip freeze --all` de tudo o que já foi instalado como restrições, para que os extras só possam adicionar pacotes, nunca mudar um. Esse passo também resolve as dependências, então falha se faltar no lock do pygeoapi algo de que um extra precisa. Nos dois casos, uma tentativa de troca faz o build falhar com `ResolutionImpossible`. Os bind mounts exigem BuildKit.
    2. Define `PROJ_DATA=/usr/share/proj`. O `pyproj` compilado não traz dados do PROJ e, diferente da `libproj` usada pelo `osgeo` e pelo `rasterio`, não procura em `/usr/share/proj` por padrão.
    3. Copia `/schemas.opengis.net` do estágio `schemas`.
    4. Copia as configurações e os scripts listados abaixo e cria `/var/lib/pygeoapi`, com escrita para o grupo 0. O `docker-entrypoint.d/` é copiado com `--chmod=755`, então todo script dali vira executável e roda num processo filho. Um script que precise ser carregado com `source` exige outro `COPY`, sem o `x`.
    5. Define `USER 1000:0`, `PYGEOAPI_LISTEN_PORT` (`ARG` e `ENV`, padrão 8000), `EXPOSE ${PYGEOAPI_LISTEN_PORT}`, `HEALTHCHECK` e `CMD ["uwsgi", "--ini", "/var/lib/uwsgi/uwsgi.conf"]`. O `ENTRYPOINT` é herdado da imagem base.
- `requirements/extra/requirements.in`: dependências extras, editadas à mão e com versões exatas: providers e o servidor de aplicação. Não vai para o contexto de build. O build instala os locks gerados a partir dele, descritos abaixo. Hoje são o `opensearch-dsl` (provider OpenSearch) e o `uWSGI`, que só existe como código-fonte e é compilado no estágio `wheels`. Não use o `pyuwsgi`, que é a versão em wheel binária: a preferência do projeto é compilar. O binário compilado usa `libpcre2-8`, `libssl3`, `libxml2` e `libpython3.12`, todos presentes na imagem de runtime. Ao mudar a versão do uWSGI ou da base, confira com `ldd $(command -v uwsgi)` na imagem final que nada aparece como `not found`, porque a `-devel` tem bibliotecas que o runtime não tem, como `libyaml` e `libjansson`.
- `requirements/extra/<versão>.txt`: um lock de extras por versão do pygeoapi, par do `requirements/pygeoapi/<versão>.txt`, gerado junto com ele pelo script e não editado à mão. Tem os pacotes do `requirements.in` e as dependências que só eles puxam (hoje `opensearch-py`, `opensearch-protobufs`, `grpcio`, `protobuf` e `Events`), com versão exata e hash. O uWSGI só tem o hash do sdist, conferido no estágio `wheels`. A resolução é feita contra o lock do pygeoapi da mesma versão, e o que esse lock já tem fica de fora. Assim, cada versão tem um par de locks resolvido em conjunto, e os extras de uma versão não dependem do lock de outra.
- `requirements/pygeoapi/<versão>.txt`: um lock por versão do pygeoapi, gerado e não editado à mão. O build escolhe o arquivo pelo `PYGEOAPI_VERSION`. Cada lock tem o pygeoapi e a árvore completa de dependências dele (hoje, 43 pacotes para a 0.24.0), com versão exata e o SHA-256 dos arquivos do PyPI. Ficam de fora os pacotes da imagem base (`GDAL`, `numpy`, `pyarrow`, `packaging`, `pip`, `setuptools`, `wheel`): a base já os fixa e verifica os hashes deles, e aqui eles entram só como restrições. Como cada versão tem seu lock, gerar o de uma versão nova não muda o que as outras instalam, e um rebuild de qualquer versão usa sempre as mesmas dependências.
- `requirements/update-requirements.sh`: gera os locks de uma ou mais versões do pygeoapi, o do pygeoapi e, em seguida, o dos extras de cada uma. Sem argumento, usa o `PYGEOAPI_VERSION` do Dockerfile. Também aceita versões (`0.25.0`) ou caminhos de lock (`requirements/pygeoapi/*`, para regenerar todos depois de trocar a base). Grava em `requirements/pygeoapi/` e `requirements/extra/`. O lock dos extras resolve o `requirements/extra/requirements.in` com o lock do pygeoapi da mesma versão como restrição. Com a opção `--extra`, regenera só os locks dos extras das versões indicadas, que aceita da mesma forma (sem versão, o `PYGEOAPI_VERSION` do Dockerfile; `requirements/pygeoapi/*` para todas), sem mexer nos do pygeoapi, que precisam existir. É o que se usa depois de editar o `requirements.in`. Caminhos só são aceitos quando o nome do arquivo é `<versão>.txt`, começando por um dígito. Os demais são pulados com uma mensagem. Resolve dentro da mesma imagem `-devel` do estágio `wheels`, com `pip install --dry-run --ignore-installed --report`, as versões e a data lidas dos `ARG` do Dockerfile e os pacotes da base como restrições, igual ao build. Os hashes vêm da API JSON do PyPI e cobrem o sdist e as wheels que a imagem consegue instalar: Python puro, ou cp312/`abi3` em `manylinux`, de qualquer arquitetura. Assim, o mesmo arquivo serve para amd64 e arm64. Usa o Podman, ou o Docker se não houver Podman (`CONTAINER_ENGINE` força um deles). Os arquivos de entrada vão para o container por variáveis de ambiente e o código Python, pela entrada padrão, sem bind mount.
- `.github/workflows/update-locks.yml`: mantém os locks fora do build e propõe as mudanças como PR. Roda em push no `main` que altere o Dockerfile. Se o `GDAL_VERSION`, o `PYTHON_VERSION` ou o `BASE_DATE` mudaram em relação ao `github.event.before`, regenera todos os locks. Se a última versão do pygeoapi no PyPI não tem lock, gera os dois locks dela e a torna o `PYGEOAPI_VERSION` padrão. Uma mudança só no `requirements.in` não dispara o workflow. Havendo mudança, abre um PR do branch `update-locks/<sha>` com o `gh`, sem actions de terceiros. Depois do merge, o workflow roda de novo, não encontra nada a mudar e não abre outro PR. Uma reexecução para o mesmo commit falha no `git push`, porque o branch já existe. Um push novo no Dockerfile antes do merge abre um segundo PR. Os locks só são regenerados depois do merge da troca da base, então o build do PR que muda o `GDAL_VERSION` ainda usa os locks antigos. É preciso habilitar "Allow GitHub Actions to create and approve pull requests" em Settings > Actions > General. PRs abertos com o `GITHUB_TOKEN` não disparam outros workflows.
- `.dockerignore`: lista de permissão. Ignora tudo (`*`) e libera só o que o Dockerfile copia ou monta: `requirements/` (`pygeoapi/` com os locks e `extra/` com os locks dos extras; o `update-requirements.sh` e o `requirements.in` ficam de fora com `requirements/*.sh` e `requirements/extra/*.in`), `conf/`, `docker/` e `docker-entrypoint.d/`. Ao fazer o Dockerfile usar um arquivo ou diretório novo, acrescente uma linha `!caminho` ali. Senão, o build falha com arquivo não encontrado. O Podman e o Docker leem esse arquivo.
- `conf/uwsgi.conf` → `/var/lib/uwsgi/uwsgi.conf`: carrega `pygeoapi.flask_app:APP` e escuta na porta de `PYGEOAPI_LISTEN_PORT` (padrão 8000) com o **protocolo uwsgi** (`socket = :$(PYGEOAPI_LISTEN_PORT)`, a sintaxe do uWSGI para variáveis de ambiente, não `http-socket`), para o nginx na frente (`uwsgi_pass`). `curl` direto na porta não funciona. Para HTTP direto, sobrescreva o arquivo com `http-socket = :$(PYGEOAPI_LISTEN_PORT)` e substitua também o `/usr/local/bin/healthcheck`. Usa `die-on-term`, porque no uWSGI 2.0 o SIGTERM recarrega em vez de parar. O `harakiri = 60` acompanha o `uwsgi_read_timeout 65s` do nginx do exemplo.
- `conf/pygeoapi-config.yml` → `/etc/pygeoapi/config.yml` (`PYGEOAPI_CONFIG`): configuração padrão sem coleções (`resources: {}`), com `ogc_schemas_location: /schemas.opengis.net` e `server.url` em `${PYGEOAPI_SERVER_URL:-http://localhost:8080}` (a porta do nginx do exemplo). O `server.bind` só vale para o servidor de desenvolvimento (`pygeoapi serve`); na imagem quem escuta é o uWSGI. Em produção, monte outro arquivo por cima ou aponte `PYGEOAPI_CONFIG` para outro caminho. O pygeoapi substitui `${VAR:-padrão}` por variáveis de ambiente.
- `docker-entrypoint.d/20-pygeoapi-openapi.sh`: gera o OpenAPI em `PYGEOAPI_OPENAPI` (`/var/lib/pygeoapi/openapi.yml`) a cada início, para refletir a configuração montada.
- `.github/workflows/docker-image.yml`: build, teste, scan e publicação de `docker.io/ndscprm/pygeoapi`. Chama o workflow reutilizável `nds-cprm/gdal-oci/.github/workflows/oci-image.yml@main` (entradas e funcionamento no README do gdal-oci, "Workflow reutilizável"), que constrói em runners nativos amd64 e arm64 (sem QEMU, então rasterio, pyproj e shapely compilam em minutos), publica por digest com SBOM e provenance, roda o teste de fumaça em cada arquitetura, analisa com Docker Scout e Grype (SARIF no code scanning; as vulnerabilidades só são reportadas) e só então cria as tags `<PYGEOAPI_VERSION>` e `<PYGEOAPI_VERSION>-<AAAAMMDD>` (`.2`, `.3`... no mesmo dia; nunca sobrescritas). A versão vem do `ARG PYGEOAPI_VERSION` (entrada `version-arg`). Roda por `workflow_dispatch` (também disparado pelo CI do gdal-oci, job `dispatch`, depois que ele publica tags novas da `ndscprm/gdal`, com as versões delas nas entradas `gdal_version`/`python_version`, repassadas em `build-args` como `GDAL_VERSION`/`PYTHON_VERSION`; e na entrada `base_date`, repassada como `BASE_DATE`; vazias, valem os `ARG` do Dockerfile. Hoje o gdal-oci não envia o `base_date`, então os builds disparados por ele usam a data do Dockerfile, e não as tags que ele acabou de publicar. Não há build agendado, porque uma base nova invalida todas as camadas. Atenção: os locks são resolvidos contra a base do `ARG` do Dockerfile, e o `update-locks` só roda quando ele muda; depois de um upgrade da base, atualize os `ARG`, inclusive o `BASE_DATE`, para os locks serem regenerados) e em pull requests para o `main`, que só constroem e testam (`push: false`, sem secrets nem tags; um commit novo cancela o build anterior do mesmo PR). Um push ou merge no `main` não dispara build: depois do merge de um PR do `update-locks` que muda o `PYGEOAPI_VERSION`, a imagem nova só é publicada quando o workflow for disparado. Limitações das entradas de versão: os locks só têm hashes das wheels do `PYTHON_VERSION` do Dockerfile (cp312), então um `python_version` diferente faz o build falhar com `THESE PACKAGES DO NOT MATCH THE HASHES`. Além disso, todas as execuções publicam a mesma tag `<PYGEOAPI_VERSION>`, qualquer que seja a base. Os builds de publicação compartilham o grupo de concorrência `publish`, que tem no máximo um run em andamento e um pendente. Um disparo novo cancela o que estava pendente, então, de três disparos seguidos do gdal-oci, o do meio não roda. Os labels OCI (`title`, `description`, `version`, `licenses`, `url`, e `created`, `revision` e `source` do reutilizável) são definidos aqui, não no Dockerfile, então só as imagens do CI os têm.
- `.github/scripts/smoke-test.sh`: teste de fumaça, rodado pelo CI em cada arquitetura e também local (`DOCKER=podman sh .github/scripts/smoke-test.sh <imagem>`). Confere o `User` `1000:0`, sobe o container com `--user 12345:0 --read-only --tmpfs /tmp --tmpfs /var/lib/pygeoapi` e `PYGEOAPI_SERVER_URL=http://smoke.test/pygeoapi`, espera o `healthcheck` e sobe na mesma rede o `nginx-unprivileged` com o [examples/nginx/conf/nginx/nginx.conf](examples/nginx/conf/nginx/nginx.conf) (o container do pygeoapi tem o alias de rede `pygeoapi`, o `upstream` do arquivo). Pelo nginx (`wget` dentro do container dele), pede `/`, `/conformance`, `/openapi`, `/collections`, a página HTML e um schema local, e confere que os links usam o `PYGEOAPI_SERVER_URL`. Por fim confere que o `osgeo` e o `rasterio` usam o mesmo GDAL e que o `rasterio` e o `pyproj` usam o mesmo PROJ. O GEOS do `shapely` só é impresso, não é comparado, e a ausência de `*.libs` em `site-packages` não é conferida. Antes das requisições, espera o nginx com um `sleep 2` fixo. Uma mudança no `nginx.conf` do exemplo é testada por ele.
- `docker/healthcheck` → `/usr/local/bin/healthcheck`: roda `uwsgi --socket 127.0.0.1:${PYGEOAPI_LISTEN_PORT:-8000} --nagios`, um ping no protocolo uwsgi respondido por um worker (falha se nenhum worker estiver atendendo; o código 2 do Nagios vira 1, que o Docker espera). Igual ao do mapproxy-oci. É o mesmo script para o `HEALTHCHECK` do Docker, para o Compose, o `--health-cmd` do Podman e as probes do Kubernetes e do OpenShift.
- `examples/`: exemplo de produção com Compose ([examples/README.md](examples/README.md)): `pygeoapi` (raiz somente leitura, `tmpfs` em `/tmp` e `/var/lib/pygeoapi`, healthcheck declarado no Compose) e `nginx-unprivileged` (HTTP :8080 → uwsgi :8000, `conf/nginx/nginx.conf` por bind mount). Em [examples/kubernetes/](examples/kubernetes/README.md), os mesmos dois serviços para Kubernetes e OpenShift: Deployments com `readOnlyRootFilesystem` e `emptyDir` em `/tmp` e `/var/lib/pygeoapi`, probes chamando o `healthcheck`, `enableServiceLinks: false`, o `nginx.conf` do exemplo com Compose num ConfigMap (criado com `kubectl create configmap --from-file`, sem cópia) e uma Route opcional para o OpenShift. Foi testado no minikube, inclusive com o UID arbitrário da `restricted-v2`. A seção "Sistema de arquivos somente leitura" do [examples/README.md](examples/README.md#sistema-de-arquivos-somente-leitura) resume os caminhos graváveis em cada runtime. O `.dockerignore` deixa `examples/` fora do contexto de build.

Build args e seus valores padrão: `GDAL_VERSION=3.12.4`, `PYTHON_VERSION=3.12`, `BASE_DATE=20261026`, `PYGEOAPI_VERSION=0.24.0`, `PYGEOAPI_LISTEN_PORT=8000`, `OGC_SCHEMAS_SHA256` (hash do zip dos schemas) e `NO_BINARY=rasterio,pyproj,shapely`.

O `SCHEMAS_OPENGIS_NET.zip` não tem versão e é substituído no servidor sem aviso. O `OGC_SCHEMAS_SHA256` é atualizado à mão, e o comentário acima dele registra o `Last-Modified` e o tamanho do arquivo conferido. Quando o arquivo mudar, o build para com `SCHEMAS_OPENGIS_NET.zip is <hash>, expected <hash>`. Nesse caso:
1. Baixe o zip novo e confira o que mudou em `ogcapi/`.
2. Atualize o hash com `curl -fsSL https://schemas.opengis.net/SCHEMAS_OPENGIS_NET.zip | sha256sum`.
3. Atualize também o `Last-Modified` e o tamanho no comentário (`curl -sI`).

Builds com cache não baixam o zip de novo enquanto o `ARG` não mudar, então a troca no servidor só aparece num build sem cache, como no CI. Mantenha o formato `ARG NOME=valor` nas linhas do `GDAL_VERSION`, do `PYTHON_VERSION`, do `BASE_DATE` e do `PYGEOAPI_VERSION`: o script as lê, e o workflow `update-locks` as compara entre commits e reescreve a do `PYGEOAPI_VERSION` com `sed`. O `--build-arg PYGEOAPI_VERSION=...` funciona para qualquer versão que tenha lock em `requirements/`.

## Build e execução

```sh
podman build -t pygeoapi-oci .        # ou docker build
podman build --build-arg PYGEOAPI_VERSION=0.25.0 -t pygeoapi-oci:0.25.0 .   # requer requirements/pygeoapi/0.25.0.txt
cd examples/nginx && PYGEOAPI_IMAGE=pygeoapi-oci podman compose up -d   # nginx em http://localhost:8080
DOCKER=podman sh .github/scripts/smoke-test.sh pygeoapi-oci               # o mesmo teste do CI
```

A porta 8000 (`PYGEOAPI_LISTEN_PORT`) fala o protocolo uwsgi, então `curl` direto nela não funciona: teste pelo nginx do exemplo, com `curl localhost:8080/?f=json`, `/conformance`, `/openapi`, `/collections`, e um schema local como `/schemas/ogcapi/features/part1/1.0/openapi/schemas/landingPage.yaml`. Também `podman exec <container> healthcheck`.

O `podman build` usa o formato OCI por padrão e avisa que vai ignorar o `HEALTHCHECK`. Para manter o `HEALTHCHECK`, use `--format docker`. Para rodar com o Podman sem Compose, declare o healthcheck com `--health-cmd healthcheck` (exemplo completo em [examples/README.md](examples/README.md#podman-sem-compose)).

## Variáveis de ambiente

- `PYGEOAPI_SERVER_URL` (padrão `http://localhost:8080`, o nginx do exemplo): URL pública, base de todos os links gerados pela API. O pygeoapi não lê `Host` nem `X-Forwarded-*`: atrás do nginx (e de um terminador TLS ou balanceador), ela precisa ser o endereço que o cliente usa, com o esquema, a porta se não for a padrão e o subcaminho, se houver (veja [examples/README.md](examples/README.md#subcaminho)).
- `PYGEOAPI_LOGLEVEL` (padrão `ERROR`).
- `PYGEOAPI_LISTEN_PORT` (padrão 8000): porta em que o uWSGI escuta, com o protocolo uwsgi. É o único lugar da porta na imagem: o `uwsgi.conf`, o `healthcheck` e o `EXPOSE` a leem. Pode ser trocada no build (`--build-arg PYGEOAPI_LISTEN_PORT=...`, que também muda o `EXPOSE`) ou ao rodar (`-e PYGEOAPI_LISTEN_PORT=...`, sem mudar o `EXPOSE`, que é só metadado). Fora da imagem, o `upstream` do nginx do exemplo continua fixo em 8000 e precisa acompanhá-la. O nome evita o prefixo `UWSGI_`, que o uWSGI interpretaria como uma opção dele, e também `PYGEOAPI_PORT`: o Kubernetes injeta essa variável, com valor `tcp://<ip>:8000`, em todo pod de um namespace que tenha um Service chamado `pygeoapi`. Com ela, o uWSGI escutava no IP do Service e o healthcheck falhava (visto no minikube). Os manifestos de [examples/kubernetes/](examples/kubernetes/) também usam `enableServiceLinks: false`. O `server.bind.port` do `pygeoapi-config.yml` não a usa, porque só vale para o `pygeoapi serve`.
- `UWSGI_PROCESSES` (padrão 4) e `UWSGI_THREADS` (padrão 2). No `uwsgi.conf`, os padrões ficam em blocos `if-not-env`, porque as opções definidas no `.ini` prevalecem sobre as variáveis `UWSGI_*`. Para mudar outras opções do uWSGI, acrescente-as ao `CMD` (`uwsgi --ini /var/lib/uwsgi/uwsgi.conf --harakiri 120`), já que as opções da linha de comando aplicadas depois do `--ini` prevalecem.

## Pendências e armadilhas

As pendências abertas ficam no [TODO.md](TODO.md). Ao resolver uma, remova-a de lá, já que o histórico fica no git, e atualize este arquivo se o comportamento da imagem mudar.

- Um `ARG` declarado antes do primeiro `FROM` só vale para as linhas `FROM`. Para usá-lo dentro de um estágio, repita `ARG NOME` depois do `FROM`, como já é feito com o `PYGEOAPI_VERSION`. Sem isso, a instalação roda como `pip install "pygeoapi=="` e falha.
- A imagem roda como `USER 1000:0`, sem privilégios. O UID 1000 não está no `/etc/passwd` de propósito: o `10-enable-nss-wrapper.sh` da base cria em tempo de execução um usuário virtual para qualquer UID que não esteja lá. O nome vem de `USER_NAME` (padrão `sgb`), com `HOME=/tmp` e `LD_PRELOAD=libnss_wrapper.so`. Isso vale também para os UIDs arbitrários do OpenShift (`--user 1000740000:0` foi testado). O grupo 0 é o que tem escrita em `/var/lib/pygeoapi`. No Podman, o resultado é diferente: com um UID que não existe na imagem, ele acrescenta `1000:*:1000:0:container user:/` ao `/etc/passwd` do container, e o nss-wrapper não é ativado. O `HOME` fica `/`, sem permissão de escrita. Hoje nada na imagem grava no `HOME`. Com `--passwd=false`, o Podman se comporta como o Docker, e o nss-wrapper é ativado.
- Com `--read-only`, o container precisa de `tmpfs` ou volume em `/var/lib/pygeoapi`, onde o OpenAPI é gerado a cada início, e em `/tmp`, onde o nss-wrapper cria o passwd virtual. Sem o `/tmp` gravável, o container sai logo no início. O Podman monta `tmpfs` em `/tmp` sozinho com `--read-only`, mas o Docker e o Kubernetes não. No Kubernetes e no OpenShift, use `readOnlyRootFilesystem: true` com um `emptyDir` em cada caminho, como em [examples/kubernetes/pygeoapi.yaml](examples/kubernetes/pygeoapi.yaml).
- A imagem final tem cerca de 776 MB, dos quais 598 MB vêm da imagem base. Eram 915 MB antes de compilar o `rasterio`, o `pyproj` e o `shapely` contra a base. A `-devel` tem cerca de 2,4 GB, mas só é usada no build.

## Dependências Python

A instalação tem três camadas, cada uma presa às anteriores:

1. **Base:** os pacotes da imagem base. As restrições são geradas no build e acompanham a tag da base, sem arquivo no repositório.
2. **pygeoapi:** o lock `requirements/pygeoapi/${PYGEOAPI_VERSION}.txt`, gerado pelo script, com o pygeoapi e cada dependência dele fixados e com hash. O `pip wheel` do estágio `wheels`, que baixa os arquivos, roda em modo de hashes (`--require-hashes`). O `pip install` final usa o lock sem hashes, porque as wheels compiladas ali não teriam hash do PyPI para bater.
3. **Extras:** o `requirements/extra/requirements.in`, editado à mão, e o lock gerado a partir dele para cada versão, `requirements/extra/${PYGEOAPI_VERSION}.txt`, com hashes, conferidos no estágio `wheels` como os do pygeoapi. É instalado por último e só pode acrescentar pacotes.

Fluxo (o workflow `update-locks` faz os dois primeiros casos sozinho quando o Dockerfile muda no `main`; à mão, o fluxo é o mesmo):
- **Nova versão do pygeoapi:** rode `./requirements/update-requirements.sh <versão>`, faça o build com `--build-arg PYGEOAPI_VERSION=<versão>` e commite os dois locks novos (`pygeoapi/` e `extra/`). Para torná-la a padrão, mude o `ARG` no Dockerfile. Os locks das versões anteriores continuam como estão.
- **Troca da tag da imagem base** (`GDAL_VERSION`, `PYTHON_VERSION` ou `BASE_DATE`): rode `./requirements/update-requirements.sh requirements/pygeoapi/*` para regenerar todos os locks, os do pygeoapi e os dos extras, já que eles dependem dos pacotes da base. Para usar um build mais novo da mesma base, com correções do Debian e do Python, avance o `BASE_DATE` para a tag datada mais recente.
- Não regenere um lock existente sem motivo. A ideia é que um rebuild da mesma versão instale as mesmas dependências.

No modo de hashes do estágio `wheels`, um lock ausente ou incompleto faz o build falhar, em vez de deixar passar algo sem versão fixa:
- `no lock file for pygeoapi X`: falta o lock dessa versão.
- `Hashes are required in --require-hashes mode`: um pacote necessário não está no lock, por exemplo depois de trocar a base sem regenerar os locks.
- `no extras lock for pygeoapi X`: falta o lock dos extras dessa versão, por exemplo num lock do pygeoapi gerado antes da divisão por versão. Regenere com `update-requirements.sh X`.
- `No matching distribution found` no `pip install` do estágio final: um extra precisa de um pacote que não está no lock dele nem no do pygeoapi, por exemplo depois de editar o lock à mão. Regenere os dois.
- `THESE PACKAGES DO NOT MATCH THE HASHES`: um arquivo baixado do PyPI não bate com o hash. Pode ser uma versão republicada ou adulteração. Investigue antes de regenerar.

Para adicionar ou atualizar um extra, edite o `requirements/extra/requirements.in` e rode `./requirements/update-requirements.sh --extra requirements/pygeoapi/*`, que regenera o lock dos extras de cada versão (ou passe só as versões que quiser). Commite o `.in` e os locks. Se o extra precisar de uma versão diferente de algo que o pygeoapi ou a base já fixam, o build falha com `ResolutionImpossible`. O `requirements.in` é o mesmo para todas as versões do pygeoapi. Se um extra não for compatível com alguma delas, o script falha ao gerar o lock dessa versão.

O uWSGI é compilado, então o hash dele só pode ser verificado no sdist, no estágio `wheels`. A wheel compilada é local e não tem hash conhecido para o `pip install` final.

O script resolve as dependências na arquitetura da máquina em que roda. Hoje nenhum pacote tem dependência condicionada à plataforma, mas, se algum passar a ter, confira o resultado nas duas arquiteturas.

## Bibliotecas geoespaciais

O `osgeo`, o `rasterio`, o `pyproj` e o `shapely` usam a mesma pilha nativa, a da imagem base: GDAL 3.12.4 (`/opt/geosgb`), PROJ 9.6.0 e GEOS 3.13.1 (pacotes do Debian), com os dados do PROJ em `/usr/share/proj` (`proj-data`). Nenhum deles traz cópias embutidas (`*.libs`), e transformações feitas pelo `pyproj` e pelo `osgeo` dão o mesmo resultado.

Versões mínimas exigidas pelas versões do lock atual:
- `rasterio` 1.5.2: GDAL 3.8 ou mais novo, para uma base com 3.12.4.
- `pyproj` 3.8.0: PROJ 9.4.0 ou mais novo (`PROJ_MIN_VERSION` no `setup.py`), para uma base com 9.6.0.
- `shapely` 2.2.0: compila e funciona com o GEOS 3.13.1.

Um lock novo, gerado pelo script ou pelo workflow, pode trazer versões que exigem bibliotecas mais novas que as da base. O script resolve contra as wheels do PyPI e não detecta isso. Nesse caso, o erro aparece como falha de compilação no estágio `wheels`, por exemplo `PROJ version ... is required`. A versão que entra é a do lock, e o comentário do `NO_BINARY` no Dockerfile registra as versões testadas (rasterio 1.5.2, pyproj 3.8.0, shapely 2.2.0). Quando um lock trouxer outras versões, confira o mínimo exigido no `setup.py` ou no `meson.build` do sdist novo, faça o build, atualize esse comentário e confira com:

```sh
podman run --rm --entrypoint python3 <imagem> -c 'import rasterio, pyproj, shapely; print(rasterio.__gdal_version__, rasterio.__proj_version__, pyproj.proj_version_str, shapely.geos_version_string)'
```

## Convenções

- Fixe a versão exata de toda dependência, tanto a imagem base, pela tag datada, quanto os pacotes Python. As dependências do pygeoapi ficam nos locks gerados em `requirements/`, um por versão, e os extras, no `requirements/extra/requirements.in`, com o lock gerado ao lado. Os pacotes da imagem base não são repetidos aqui: a base já os fixa e verifica os hashes deles.
- Mantenha as imagens portáveis entre Docker, Podman, Kubernetes e OpenShift. O Podman (no formato OCI), o Kubernetes e o OpenShift ignoram o `HEALTHCHECK`, então as verificações de saúde passam pelo script `healthcheck`, que o Compose, o `--health-cmd` do Podman e as probes podem chamar.
- Do estágio `-devel`, passe só as wheels para o estágio final, nunca o venv `/opt/geosgb/venv` inteiro. A imagem de runtime vem de um estágio da imagem base que remove os pacotes `-dev` e os símbolos de depuração: o `_gdal.so` tem 1,5 MB no runtime e 8,3 MB na `-devel`. Copiar o venv traria esses arquivos e duplicaria na nova camada os 124 MB do venv que a base já tem.
- Tudo o que precisar ser gravado em tempo de execução deve ficar em diretórios com dono do grupo 0 e `chmod g=u`, para funcionar com UIDs arbitrários.
- Scripts em `/docker-entrypoint.d`: os `*.sh` executáveis rodam num processo filho, e os não executáveis são carregados com `source`, o que permite exportar variáveis para o `CMD`. Eles rodam em ordem lexical, e uma falha impede o container de subir.
