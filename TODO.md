## Média: CI e comportamento em produção

- [ ] **Suportar outras versões do Python.** Por enquanto a imagem é só Python 3.12: o job `check` do `docker-image.yml` pula os disparos com imagens de outro Python, procurando `-py3.12` na tag (literal `PYTHON: py3.12`, a manter igual aos padrões do Dockerfile). Os locks só têm hashes das wheels cp312 (`pydantic_core`, `PyYAML`, `regex`, `rpds-py`, `MarkupSafe`, `charset-normalizer`...), e todas as execuções publicam a mesma tag `<PYGEOAPI_VERSION>`. O plano é inspecionar o código-fonte do pygeoapi para montar uma tabela fixa de requirements, e então ter locks por Python e tags com sufixo. Imagens com outro GDAL são aceitas e publicam sob a mesma tag, de propósito, para permitir subir o GDAL; a base fica registrada no label `org.opencontainers.image.base.name`.
- [ ] **Regenerar os locks depois de um disparo do gdal-oci.** O gdal-oci envia as imagens que acabou de publicar (tag datada e digest), e o build usa essas imagens. Mas os locks continuam resolvidos sobre a `-devel` do cabeçalho deles, até alguém rodar o `update-locks` à mão com o `image_devel` novo. Decidir se um build disparado com uma `-devel` diferente da dos locks deve também disparar o `update-locks` (que abre o PR com os locks regenerados).
- [ ] **Publicar depois de um merge no `main`.** O `docker-image.yml` só roda por `workflow_dispatch`, normalmente vindo do gdal-oci. Depois do merge de um PR do `update-locks` que torna uma versão nova a padrão, a imagem dela só é publicada no próximo rebuild semanal do gdal-oci, ou num disparo manual. Agora que o Dockerfile tem padrões (as tags móveis), um gatilho de `push` no `main` poderia publicar logo, mas sobre as tags móveis, e não sobre a base dos locks. Avaliar se a espera até o rebuild semanal é aceitável.
- [ ] **Medir o tempo de geração do OpenAPI na subida.** O `20-pygeoapi-openapi.sh` regenera o documento a cada início. Com muitas coleções, isso pode atrasar o início além do `--start-period=15s` do healthcheck e das probes.
- [ ] **Revisar os parâmetros do uWSGI para cargas reais.** Os valores atuais (`processes=4`, `threads=2`, `harakiri=60`, `buffer-size=32768`) são padrões razoáveis, mas não foram testados com carga real. Avalie também `max-requests` ou `reload-on-rss`, para limitar vazamento de memória em providers de raster.

## Baixa: limpeza e infraestrutura

- [ ] **Testar os PRs do `update-locks` antes do merge.** O CI não tem build de pull request: ele foi removido quando a base dependia de uma data obrigatória, e o `docker-image.yml` sempre publica. Um lock novo pode trazer uma versão de `rasterio`, `pyproj` ou `shapely` que exija GDAL, PROJ ou GEOS mais novos que os da base, e isso só aparece ao compilar. Hoje o teste é um build local do branch do PR (com os `--build-arg GDAL_IMAGE_*` da base dos locks) com o teste de fumaça. Com os padrões atuais do Dockerfile, o gatilho `pull_request` (`push: false`) poderia voltar, ou o próprio `update-locks` poderia construir a imagem.
- [ ] **Validar o `update-locks.yml` no GitHub.** Ele foi testado só numa simulação local (YAML e a lógica dos três passos, sem `git push` nem `gh pr create`). Na primeira execução real, confira a permissão para criar PRs e o push do branch.
- [ ] **Tornar o `update-locks` idempotente.** Uma reexecução para o mesmo commit falha no `git push`, porque o branch `update-locks/<sha>` já existe. Um push novo no Dockerfile antes do merge abre um segundo PR. Atualize um branch fixo com `--force-with-lease` e reaproveite o PR aberto, se houver.
- [ ] **Detectar versões novas do pygeoapi sem depender de push no Dockerfile.** Hoje o `update-locks` só roda quando o Dockerfile muda no `main`. Uma versão nova publicada no PyPI só é percebida no próximo push desse tipo. Um gatilho agendado (`schedule`) ou manual (`workflow_dispatch`) resolveria isso.
- [ ] **Conferir no CI que os locks dos extras estão em dia.** Uma edição no `requirements/extra/requirements.in` sem rodar `update-requirements.sh --extra` passa despercebida: o build só lê o `requirements/extra/<versão>.txt`. Um passo no `docker-image.yml` poderia comparar os nomes e versões do `.in` com os do lock de cada versão e falhar se divergirem.
- [ ] **Trocar o `sleep 2` do teste de fumaça por uma espera com tentativas.** Ele espera o nginx subir antes das requisições. Num runner lento, o teste pode falhar à toa.
- [ ] **Normalizar os nomes na checagem do `NO_BINARY`.** O `grep -io "^${name}=="` não trata `-` e `_` como equivalentes, e um `.` no nome vira coringa de regex. Hoje não faz diferença com `rasterio,pyproj,shapely`.
- [ ] **Ajustar o `client_max_body_size` no nginx do exemplo.** O padrão é 1 MB, e um POST de processos ou de transações maior que isso recebe `413`. Defina um valor ou explique num comentário.
