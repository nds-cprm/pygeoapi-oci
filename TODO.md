## Média: CI e comportamento em produção

- [ ] **Resolver a entrada `python_version` do `docker-image.yml`.** Os locks só têm hashes das wheels do `PYTHON_VERSION` do Dockerfile (cp312). Com outro Python, o pip escolhe wheels `cp3XX` cujos hashes não estão no lock (`pydantic_core`, `PyYAML`, `regex`, `rpds-py`, `MarkupSafe`, `charset-normalizer`...), e o build falha. Além disso, todas as execuções publicam a mesma tag `<PYGEOAPI_VERSION>`, então uma variante sobrescreveria a outra. Há três saídas: remover a entrada, falhar cedo se ela for diferente do `ARG`, ou ter locks por Python e tags com sufixo. O mesmo vale, em menor grau, para o `gdal_version`: a tag não registra a base.
- [ ] **Fazer o gdal-oci enviar a data da base.** A base agora é fixada pela tag datada (`ARG BASE_DATE`), e o `docker-image.yml` aceita a entrada `base_date`. Mas o job `dispatch` do gdal-oci envia só `gdal_version` e `python_version`, e o job `merge` dele calcula o sufixo datado (`STAMP` e `.N`) sem expô-lo como output. Até isso mudar, o rebuild semanal disparado pelo gdal-oci reconstrói a base fixada no Dockerfile, e não a que acabou de ser publicada. No gdal-oci: exportar o sufixo como output do `merge` e passar `-f base_date=...` no `gh workflow run`. Aqui: decidir se um build disparado com uma data nova também deve abrir um PR que avance o `BASE_DATE`, para que os locks sejam regenerados contra ela.
- [ ] **Não perder disparos do gdal-oci.** Todos os builds de publicação usam o grupo de concorrência `publish`, que tem no máximo um run em andamento e um pendente. Um disparo novo cancela o pendente, então, de três disparos seguidos, o do meio não roda. Inclua as versões das entradas no nome do grupo, ou faça o gdal-oci disparar uma vez só.
- [ ] **Publicar depois de um merge no `main`.** O `docker-image.yml` só roda por `workflow_dispatch` e em PRs. Depois do merge de um PR do `update-locks` que torna uma versão nova a padrão, nenhuma imagem dela é publicada até alguém disparar o workflow. Acrescente `push` no `main` com `paths` (`Dockerfile`, `requirements/**`, `conf/**`, `docker/**`, `docker-entrypoint.d/**`).
- [ ] **Conferir o GEOS e as cópias embutidas no teste de fumaça.** O `smoke-test.sh` só imprime o GEOS do `shapely`. Compare-o com o do GDAL (`ogr.GetGEOSVersionMajor()`, `Minor()` e `Micro()`) e faça o teste falhar se houver `*.libs` em `site-packages` (`rasterio.libs`, `pyproj.libs`, `shapely.libs`). Isso confirmaria que nenhuma wheel binária de um pacote do `NO_BINARY` entrou na imagem.
- [ ] **Fixar as dependências de build que não vêm da base.** O numpy, o setuptools e os demais pacotes da base já estão fixados no build com `--build-constraint`, já que o `-c` não alcança o ambiente de build isolado. Cython, meson e meson-python, usados para compilar o `rasterio`, o `pyproj`, o `shapely` e o uWSGI, continuam sem versão fixa e sem hash. No último build foram Cython 3.3.0, meson 1.12.1 e meson-python 0.22.1. Para fixá-los, crie um arquivo de restrições de build, com versões e hashes, e passe-o como um segundo `--build-constraint`.
- [ ] **Documentar o uso com sistema de arquivos somente leitura no Kubernetes e no OpenShift.** O Docker, o Podman e o Compose já estão cobertos pelo [examples/](examples/README.md) e pelo teste de fumaça (`--read-only --tmpfs /tmp --tmpfs /var/lib/pygeoapi`). Falta documentar `readOnlyRootFilesystem` com dois `emptyDir` (`/tmp` e `/var/lib/pygeoapi`) e as probes chamando o `healthcheck`. No OpenShift, confira também com o UID arbitrário da SCC `restricted-v2`.
- [ ] **Documentar o healthcheck no Podman.** O Podman ignora o `HEALTHCHECK` de imagens OCI. O Compose do exemplo já declara o healthcheck, e as imagens do CI, geradas pelo BuildKit, mantêm o `HEALTHCHECK`. Falta documentar o `podman run --health-cmd healthcheck` e lembrar do `--format docker` nos builds locais com `podman build`.

Mudar uma delas sem as outras quebra o healthcheck ou o proxy.

## Baixa: limpeza e infraestrutura

- [ ] **Build nos PRs do `update-locks`.** O `docker-image.yml` roda em pull requests (só build e teste), mas PRs abertos com o `GITHUB_TOKEN` não disparam outros workflows, então os do `update-locks` não são construídos. Um lock novo pode trazer uma versão de `rasterio`, `pyproj` ou `shapely` que exija GDAL, PROJ ou GEOS mais novos que os da base, e isso só aparece ao compilar. Use um token de GitHub App ou PAT no `update-locks`, ou dispare o `docker-image.yml` à mão no branch do PR. Relacionado: os locks só são regenerados depois do merge da troca da base, então o PR que muda o `GDAL_VERSION` é construído com os locks antigos e pode falhar se a base nova mudar um pacote do lock.
- [ ] **Validar o `update-locks.yml` no GitHub.** Ele foi testado só numa simulação local (YAML e a lógica dos três passos, sem `git push` nem `gh pr create`). Na primeira execução real, confira a permissão para criar PRs e o push do branch.
- [ ] **Tornar o `update-locks` idempotente.** Uma reexecução para o mesmo commit falha no `git push`, porque o branch `update-locks/<sha>` já existe. Um push novo no Dockerfile antes do merge abre um segundo PR. Atualize um branch fixo com `--force-with-lease` e reaproveite o PR aberto, se houver.
- [ ] **Detectar versões novas do pygeoapi sem depender de push no Dockerfile.** Hoje o `update-locks` só roda quando o Dockerfile muda no `main`. Uma versão nova publicada no PyPI só é percebida no próximo push desse tipo. Um gatilho agendado (`schedule`) ou manual (`workflow_dispatch`) resolveria isso.
